## CRITICAL: Never replace — only update the UI layer

**Every session starts with zero memory of previous work.**
The backend wiring, auth logic, DB queries, and API calls in each file were
built across many sessions. They must NEVER be lost.

### Rule: When a .dc.html arrives, do a surgical UI update — not a rewrite

**Before editing any file**, state out loud:
> "Update the UI layer in `[file]` to match the new design — preserve all backend wiring."

Then follow this sequence:

1. **Read the existing `.tsx` file first** — understand what backend logic is already there
2. **State explicitly what will be preserved** — list auth gates, API calls, DB queries present
3. **Identify only what changed visually** — layout, copy, colors, new components
4. **Edit only those parts** — use the Edit tool, not Write/overwrite
5. **Preserve everything else** — API fetches, auth checks, state management, error handling, DB queries

If a page needs a full rewrite because the design is fundamentally different,
explicitly list every piece of backend logic being preserved before touching anything.

## Infrastructure (already configured — do not reconfigure)

- **Database:** Supabase Postgres at `db.bjkabtzvgfshsrmjhrkx.supabase.co` — 99 migrations in `prisma/migrations`, all tables exist.
- **A single failed migration stops ALL production deploys — this happened, and went unnoticed for a day.** On 2026-07-27 a session applied `20260726120000_add_advertiser_category_pitch` out of band via the Supabase MCP (see DESIGN_SYNC row 250), which is exactly what the `apply_migration` de-allowlisting below exists to prevent. CI later re-ran the same file through `prisma migrate deploy`; `CREATE TYPE "AdvertiserCategory"` hit the type that already existed and failed with SQLSTATE **42710** (duplicate_object), leaving a `finished_at IS NULL` row in `_prisma_migrations`. From then on every deploy failed with **P3009** at the migrate step — and because the Cloudflare deploy, cron deploy, smoke test and cache purge all come *after* it in the job, they were skipped. **Production shipped nothing for a day** while three PRs merged green. Recovery: confirm the DDL really is in the database, then run the **"Resolve a failed migration"** workflow (Actions tab, `workflow_dispatch`) with the migration name — it calls `scripts/resolve-failed-migration.mjs`, which refuses to act unless `prisma migrate status` itself reports that migration as failed. The deploy workflow now detects P3009 and fails immediately with that instruction instead of retrying a permanent error three times behind a generic message.
- **Every migration in `prisma/migrations/` is applied to production automatically** (as long as the migrate step is passing — see the row above)**.** `.github/workflows/deploy-production.yml` runs `prisma migrate deploy` on every push to `main`. There is no manual apply step and never was. A "DO NOT APPLY BLIND" comment in a migration header does **not** gate anything on its own — three migrations carried such comments and all three shipped on merge, including two that drop data (`20260714020000_drop_ad_submission`, `20260714050000_drop_ad_image_url`) and `20260727120000_enable_rls_all_tables`. Earlier revisions of this file described the first two as unapplied; that was wrong.
- **There is a second, vendor-managed schema in this database: `stripe`.** It is the Supabase **Stripe Sync Engine** (~25 synced tables — `charges`, `invoices`, `payment_intents`, … — plus its own `stripe._migrations`), installed outside this repo and not referenced by any application code: iHYPE talks to Stripe through the Node SDK (`src/lib/stripe.ts`), never through these tables. Do not add it to `schema.prisma` and do not assume changes to it survive — the sync engine runs its own migrations and may `CREATE OR REPLACE` its functions at any upgrade.
- **Supabase advisor findings are worth reading twice before acting.** The 2026-07-28 run reported `public.rls_auto_enable()` as executable by `anon` "via `/rest/v1/rpc/rls_auto_enable`". The grants were real, but the function `RETURNS event_trigger`, and PostgreSQL refuses to invoke those outside the event-trigger manager — verified against production: `ERROR: 0A000: trigger functions can only be called as triggers`. So it was a wrong grant, not a reachable path. It was revoked anyway (`20260728210000_harden_function_grants_and_search_path`), along with pinning `search_path` on the three `stripe` trigger helpers. The revoke does not stop the `ensure_rls` event trigger firing: EXECUTE on a trigger function is checked when the trigger is created, not each time it fires — verified on a local Postgres fixture before shipping.
- **A migration that touches objects it may not own must fail soft.** `ALTER FUNCTION`/`REVOKE` need ownership, and the four functions above are owned by `postgres` while migrations run as whatever `DIRECT_URL` authenticates as. A permission error would leave a failed row in `_prisma_migrations` and **block every subsequent production deploy** — far worse than the warning it was clearing. That migration therefore wraps each statement in an exception handler that degrades to `RAISE WARNING`. The cost is that a green deploy no longer proves it applied: re-run the Supabase advisor to find out.
- **First real use of the gating workflow:** `prisma/migrations-pending/20260728201000_drop_ad_clicks` (drops `Ad.clicks`, dead since the banner-ad system was retired — an audio spot has no click-through, and `/admin/ads` was rendering a permanent `0 clicks` beside a real impression count). The field is already out of `schema.prisma` and out of the UI, so the *code* half is deployed; the column drop waits for someone to confirm `SELECT count(*) FROM "Ad" WHERE "clicks" <> 0` is 0 and then `git mv` it across.
- **To gate a migration, park it in `prisma/migrations-pending/`** — Prisma never reads that directory. `npm run guard:migrations` (`scripts/check-gated-migrations.mjs`, wired into CI and into the production deploy immediately before the migrate step) fails the build if a migration marked `@gated` sits in `prisma/migrations/`. Applying one is a deliberate `git mv` back, in its own commit. See `prisma/migrations-pending/README.md`.
- **The Prisma MCP server is REMOVED — do not re-add it (2026-08-06).** `.mcp.json` used to register `prisma` (stdio, `npx prisma mcp`). It exposed exactly three tools and earned nothing: `Prisma-Studio` is a local UI and useless in a remote session, `migrate-status` was the only one allowlisted, and **`migrate-dev` is actively dangerous** — it writes a new migration straight into `prisma/migrations/`, the directory that auto-deploys on every push to `main`, and can reset or drop the database it points at, bypassing the `migrations-pending/` gating workflow entirely. Carrying a server whose one useful tool is a status read, and whose second tool can drop the production database, is a bad trade; the whole entry is gone. **Write migrations by hand into `prisma/migrations-pending/`, and read data through the Supabase MCP** — the Prisma one never had a query tool at all, which is why it could not answer a single question anyone actually asked of it. Note this removes only the MCP *server*: the Prisma ORM and Prisma Migrate are load-bearing (309 files import `@/lib/db`; 109 migrations deploy on every push) and are not going anywhere.
- **Do not add Prisma's *remote* MCP server (`https://mcp.prisma.io/mcp`) either — it is a different product.** Prisma ships two MCP servers; the local one is removed per the bullet above, and this is the other. The remote one is the management API for **Prisma Postgres**, Prisma's own hosted database product, and authenticates via OAuth to a Prisma Console workspace on first use. Its tools (`CreateDatabase`/`DeleteDatabase`/`ListDatabases`, `CreateBackup`/`ListBackups`/`CreateRecovery`, `Create`/`Delete`/`ListConnectionStrings`, `ExecuteSqlQuery`, `IntrospectSchema`, `search_prisma_documentation`) act on databases inside that workspace. iHYPE's database is Supabase Postgres behind Cloudflare Hyperdrive — there is no Prisma Postgres instance for any of those tools to reach, so the only thing connecting it would add is an OAuth-gated, write-capable database surface (`ExecuteSqlQuery`, `DeleteDatabase`) sitting outside both the `read_only=true` pin below and the `migrations-pending/` gating workflow above. Note also that adding it the documented way — claude.ai → Connect apps → **+ Add integration** — installs it as a per-account connector, so it would **not** appear in `.mcp.json` and this repo would have no record of it; that is why the decision is written down here. If iHYPE ever actually moves onto Prisma Postgres, revisit this bullet.
- **REVISITED 2026-08-06 — a Prisma Postgres instance now exists, and the bullet above is out of date on that one point.** A **`Prisma Compute Deploy`** check started appearing on pull requests at 12:22 UTC that day (first seen on PR #648; nothing in this repo was changed to cause it). It is an account-level GitHub integration, which is precisely the "this repo would have no record of it" failure mode the bullet above predicted. - **The Supabase MCP server is pinned to `read_only=true`** in `.mcp.json`, which makes Supabase run every query as a read-only Postgres user — enforced at the database, not just by withholding tools. `mcp__supabase__apply_migration` was **removed from the `.claude/settings.json` allowlist** for the same reason `migrate-dev` was never added: it applies DDL straight to the production database, bypassing the `migrations-pending/` gating workflow and version control entirely. Schema changes belong in `prisma/migrations/` in git, deployed by CI — never through an MCP tool call. Do not drop `read_only=true` or re-add `apply_migration` to make a write "just work"; write the migration file instead. **`read_only` is scoped to SQL only** — Supabase documents it as "execute all queries as a read-only Postgres user", and says nothing about the non-SQL tools. The four kept groups supply every allowlisted tool (`execute_sql`/`list_tables` from `database`, `get_advisors` from `debugging`). Widening `features=` re-opens a write path that `read_only` does not close.

## DO / DO NOT

| DO | DO NOT |
|---|---|
| **Read the existing .tsx before touching it** | **Overwrite a file without reading it first** |
| Use Edit tool for UI updates | Use Write tool to replace whole files |
| Translate .dc.html faithfully to .tsx | Invent UI not shown in .dc.html |
| Use `var(--*)` CSS tokens from design system | Hardcode colors or type sizes |
| Wire real API to existing mock data shapes | Change data structure without design update |
| Add `admin@ihype.org` for all contact | Use any other email address |
| Keep split as 70/20/10 / 0% iHYPE | Change the revenue split in any copy |
| Use audio-only for radio/live | Add video hosting or live video |
| Reference `ihype.org` only | Use any other domain |
| Preserve auth gates and DB queries on UI updates | Remove or replace backend logic during UI syncs |

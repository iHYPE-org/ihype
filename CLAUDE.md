## CRITICAL: Never replace — only update the UI layer

**Every session starts with zero memory of previous work.**
The backend wiring, auth logic, DB queries, and API calls in each file were
built across many sessions. They must NEVER be lost.

### Rule: When a .dc.html arrives, do a surgical UI update — not a rewrite

**Before editing any file**, state out loud:
> "Update the UI layer in `[file]` to match the new design — preserve all backend wiring."

Then follow this sequence:

1. **Read the existing `.tsx` file first** — understand what backend logic is already there
2. **State explicitly what will be preserved** — list auth gates, API calls, DB queries present
3. **Identify only what changed visually** — layout, copy, colors, new components
4. **Edit only those parts** — use the Edit tool, not Write/overwrite
5. **Preserve everything else** — API fetches, auth checks, state management, error handling, DB queries

If a page needs a full rewrite because the design is fundamentally different,
explicitly list every piece of backend logic being preserved before touching anything.

- **The Prisma MCP server is REMOVED — do not re-add it (2026-08-06).** `.mcp.json` used to register `prisma` (stdio, `npx prisma mcp`). It exposed exactly three tools and earned nothing: `Prisma-Studio` is a local UI and useless in a remote session, `migrate-status` was the only one allowlisted, and **`migrate-dev` is actively dangerous** — it writes a new migration straight into `prisma/migrations/`, the directory that auto-deploys on every push to `main`, and can reset or drop the database it points at, bypassing the `migrations-pending/` gating workflow entirely. Carrying a server whose one useful tool is a status read, and whose second tool can drop the production database, is a bad trade; the whole entry is gone. **Write migrations by hand into `prisma/migrations-pending/`, and read data through the Supabase MCP** — the Prisma one never had a query tool at all, which is why it could not answer a single question anyone actually asked of it. Note this removes only the MCP *server*: the Prisma ORM and Prisma Migrate are load-bearing (309 files import `@/lib/db`; 109 migrations deploy on every push) and are not going anywhere.
- **Do not add Prisma's *remote* MCP server (`https://mcp.prisma.io/mcp`) either — it is a different product.** Prisma ships two MCP servers; the local one is removed per the bullet above, and this is the other. The remote one is the management API for **Prisma Postgres**, Prisma's own hosted database product, and authenticates via OAuth to a Prisma Console workspace on first use. Its tools (`CreateDatabase`/`DeleteDatabase`/`ListDatabases`, `CreateBackup`/`ListBackups`/`CreateRecovery`, `Create`/`Delete`/`ListConnectionStrings`, `ExecuteSqlQuery`, `IntrospectSchema`, `search_prisma_documentation`) act on databases inside that workspace. iHYPE's database is Supabase Postgres behind Cloudflare Hyperdrive — there is no Prisma Postgres instance for any of those tools to reach, so the only thing connecting it would add is an OAuth-gated, write-capable database surface (`ExecuteSqlQuery`, `DeleteDatabase`) sitting outside both the `read_only=true` pin below and the `migrations-pending/` gating workflow above. Note also that adding it the documented way — claude.ai → Connect apps → **+ Add integration** — installs it as a per-account connector, so it would **not** appear in `.mcp.json` and this repo would have no record of it; that is why the decision is written down here. If iHYPE ever actually moves onto Prisma Postgres, revisit this bullet.
- **REVISITED 2026-08-06 — a Prisma Postgres instance now exists, and the bullet above is out of date on that one point.** A **`Prisma Compute Deploy`** check started appearing on pull requests at 12:22 UTC that day (first seen on PR #648; nothing in this repo was changed to cause it). It runs `prisma migrate deploy` against a Prisma Postgres database at **`db.prisma.io:5432`**, replaying every migration in `prisma/migrations/` — 109 of them at the time of writing — into a Prisma Console workspace (`console.prisma.io/cmmmd9o5u04g2yye9iy9mkv4k`). **Nothing in this repository references it**: not `prisma.config.ts`, not `.mcp.json`, not any workflow. It is an account-level GitHub integration, which is precisely the "this repo would have no record of it" failure mode the bullet above predicted. Consequences worth knowing: (1) there is now a **second database** receiving this schema, so "the database" is ambiguous — production is still Supabase behind Hyperdrive, and `src/lib/stripe.ts`-style app code never talks to Prisma Postgres; (2) anything moved out of `prisma/migrations-pending/` into `prisma/migrations/` will be applied **there** as well as in production, so the gating workflow now gates two targets; (3) its failures are **not** production deploy failures — the first one (PR #650) was `P1002`, a 10-second advisory-lock timeout, i.e. a transient concurrency fault on their side, and it had passed twice before. **Do not treat a red `Prisma Compute Deploy` as a P3009-class blocker** — check `_prisma_migrations` in Supabase before concluding anything about production. If this integration is not wanted, it is removed from the Prisma Console workspace or the repo's GitHub App settings, not from this codebase.
- **The Supabase MCP server is pinned to `read_only=true`** in `.mcp.json`, which makes Supabase run every query as a read-only Postgres user — enforced at the database, not just by withholding tools. `mcp__supabase__apply_migration` was **removed from the `.claude/settings.json` allowlist** for the same reason `migrate-dev` was never added: it applies DDL straight to the production database, bypassing the `migrations-pending/` gating workflow and version control entirely. Schema changes belong in `prisma/migrations/` in git, deployed by CI — never through an MCP tool call. Do not drop `read_only=true` or re-add `apply_migration` to make a write "just work"; write the migration file instead. **`read_only` is scoped to SQL only** — Supabase documents it as "execute all queries as a read-only Postgres user", and says nothing about the non-SQL tools. That is why the URL also pins `features=database,debugging,development,docs`: the omitted groups (`account`, `branching`, `functions`) carry write operations — project management, branch create/delete, `deploy_edge_function` — that run through the Management API rather than Postgres, so the read-only role cannot be assumed to cover them. The four kept groups supply every allowlisted tool (`execute_sql`/`list_tables` from `database`, `get_advisors` from `debugging`). Widening `features=` re-opens a write path that `read_only` does not close.
